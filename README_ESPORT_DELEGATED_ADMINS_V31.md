- tanadon@chiangkham.ac.th
- tanamas@chiangkham.ac.th

- anuphan@chiangkham.ac.th

ทั้งสี่อีเมลจะถูกเพิ่มเป็น **รายชื่อที่อนุญาต** โดย SQL Migration 0025 แต่ยังไม่สามารถแก้ไขข้อมูลได้จนกว่าจะล็อกอินด้วย Google ที่ยืนยันอีเมลแล้ว และติดตั้ง SQL + หน้าเว็บสำเร็จ

## อำนาจ

- จัดการคู่แข่งขัน RoV ชายและหญิง: วัน/เวลา, โปรแกรม, ผล, คะแนน, Knockout, ลำดับแข่ง, การเผยแพร่ และประวัติ
- เข้าถึงรายชื่อนักกีฬาและภาพส่วนตัวของทีม RoV ตามสิทธิ์ที่ Admin หลักมี
- ใช้การรีเซตข้อมูลทดสอบ RoV ตามข้อจำกัดและขั้นตอนยืนยันเดิม (ใช้ไม่ได้ตั้งแต่ 5 ธ.ค. 2569)
- **ไม่มีสิทธิ์** เป็น `competition_admin` หรือ `super_admin` และไม่มีสิทธิ์แก้ไขกีฬาประเภทอื่น ข้อมูลโรงเรียน หรือสิทธิ์หลัก
- การเพิ่มและถอนผู้ดูแล E-Sport คนอื่นทำได้เฉพาะ **Admin หลัก** ที่หน้า E-Sport → **ผู้ดูแล E-Sport**

## ติดตั้ง

1. สำรองฐานข้อมูล Supabase (ควรทดลองใน Preview / ฐานข้อมูลทดสอบก่อน)
2. ตรวจว่ามี Migration 0024 จาก v30.3 แล้ว
3. เปิด Supabase SQL Editor แล้วรันไฟล์ `supabase/migrations/202611220025_esports_delegated_admins.sql` ทั้งไฟล์ **ครั้งเดียว** (ทำรายการโครงสร้างสิทธิ์และเพิ่มอีเมล; ไม่ลบข้อมูลใด)
4. แตก Patch v31 ทับโครงการ **v30.5** (หรือใช้ ZIP ฉบับเต็ม v31 แทน)
5. Commit → Push ผ่าน GitHub Desktop และตรวจว่า Vercel Preview Build ผ่าน แล้วจึง Promote
6. เข้า `https://<your-domain>/group-sports/esports` ด้วย Admin หลัก → เมนู **ผู้ดูแล E-Sport** แล้วตรวจรายชื่อ 4 คน
7. ให้กรรมการแต่ละคนใช้ Google Sign-in ที่ `/login` และตรวจว่าเข้าสู่ `/group-sports/esports` ได้
8. ทดลองด้วยบัญชีกรรมการ: ดูคู่ฉบับร่าง, บันทึกผลในสภาพแวดล้อมทดสอบ, ดูประวัติ แล้วลองเข้าหน้าจัดการกีฬาประเภทอื่นเพื่อยืนยันว่า **ไม่มีสิทธิ์**
9. ทดสอบถอนสิทธิ์กรรมการ 1 คนและให้รีเฟรชหน้า ตรวจว่าแก้ไข RoV ไม่ได้ จากนั้นเปิดสิทธิ์กลับคืน

## เพิ่มในภายหลัง

Admin หลัก → E-Sport → **ผู้ดูแล E-Sport** → กรอกอีเมล Google ของกรรมการ → **เพิ่ม / เปิดสิทธิ์**

สามารถถอนสิทธิ์และเปิดสิทธิ์กลับคืนได้จากรายการด้านล่างโดยไม่แก้ SQL หรือโค้ด หากผู้สมัครไม่เคยล็อกอิน Google มาก่อน ให้เพิ่มรายชื่อล่วงหน้าได้ ระบบจะตรวจสอบอีกครั้งตอนลงชื่อเข้าใช้

## ความปลอดภัยและข้อจำกัด

- สิทธิ์ตรวจที่ **Supabase RLS และ Security-Definer RPC** ไม่ได้ใช้เพียงการซ่อนปุ่ม
- การพิสูจน์ตัวตนใช้อีเมลที่ยืนยันแล้วพร้อม Google identity จาก Supabase Auth ไม่อาศัยโดเมนหรือ user_metadata
- บัญชีอื่นไม่สามารถเพิ่มตนเองเป็นผู้ดูแลได้ และการเปลี่ยนสิทธิ์มี audit log
- หากบริษัทใช้ Google Workspace จำกัดการเข้าถึง OAuth แอปตามโดเมน ต้องอนุญาตบัญชีนอกโดเมนด้วยในหน้า Google/Supabase ตั้งค่าของผู้ดูแลก่อน
- **ยังไม่ทดสอบ migration กับฐานข้อมูล Production** ตรวจสอบ RLS และ OAuth ก่อนใช้งานจริง
